# Contract Review with GitHub Copilot Harness - Runbook

## Prerequisites

Before implementation, confirm:

- GitHub Copilot Harness is available for the intended Copilot Studio environment.
- Required entitlements, authoring methods, tools, and deployment channels are supported.
- A cost owner has approved Copilot Credit capacity and controls before AI-assisted authoring, testing, or evaluation.
- Legal owns the standard-position library, fallback wording, and risk taxonomy.
- A qualified reviewer and operational owner are assigned.
- Contract and reference sources are authorized for the intended processing boundary.
- Representative test documents are available.
- A review system can enforce approval independently of the agent.
- Approved persistent storage can retain review artifacts and approval records for the required legal retention period.

Start with one contract type and one jurisdictional scope.

Usage by GitHub Copilot harness agents isn't included with a user's Microsoft 365 Copilot license. Follow the [execution runbook's capacity setup](../../02-patterns/GitHub-Copilot-Harness-Execution/GitHub-Copilot-Harness-Execution-Runbook.md#prerequisites) before building.

Record the [deployment path](../../02-patterns/GitHub-Copilot-Harness-Execution/GitHub-Copilot-Harness-Execution-Runbook.md#record-the-deployment-path), including the model, environment region/data movement, authentication, selected channel, and feature-by-feature preview status. Follow the official [model selection controls](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/authoring-select-agent-model) and [channel support table](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/publication-channels-overview).

For automation, use a [Copilot Studio Workflow Agent node](https://learn.microsoft.com/en-us/microsoft-copilot-studio/workflows-experience/agent-node-workflow). The [Power Automate Microsoft Copilot Studio connector doesn't support invoking GitHub Copilot harness agents](https://learn.microsoft.com/en-us/power-automate/call-copilot-studio-agent). An interactive deployment still needs a supported, authenticated channel.

## Phase 1 - Establish the Review Contract

Agree on:

1. Required inputs and approved sources.
2. Clause types to review.
3. Classification and severity definitions.
4. Permitted fallback wording.
5. Mandatory escalation conditions.
6. Output format and reviewer responsibilities.
7. Baseline measures and release thresholds.

Make the legal boundary explicit: the agent prepares analysis for qualified review; it does not make final legal decisions.

Record which clause categories require counsel before replacement wording is drafted. The example policy uses liability, indemnity, and intellectual property. Define how these become `RED_LINE` findings with withheld fallback text, and confirm that historical agreements don't override approved positions.

**Exit criteria:** Legal has approved the scope, taxonomy, output contract, and review boundary.

## Phase 2 - Configure Sources and Read Tools

On the Copilot Studio home page, select an environment where you have creation permission and create an agent powered by the GitHub Copilot harness. This is a creation-time choice; an existing standard harness agent can't be switched to this harness.

In **Build**, configure **Instructions** and **Model**, add approved sources under **Knowledge**, and add authorized retrieval operations under **Tools**. Implement supported connections to the contract and standards sources.

There is [no general-knowledge on/off setting for this harness](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/knowledge-add-existing-copilot). Configuring approved sources is not, by itself, a guarantee that every generated claim is grounded. Enforce this design's evidence requirements through instructions, retrieval scope, output validation, and review.

Logical tool responsibilities may include:

| Responsibility | Illustrative interface name | Required behavior |
|---|---|---|
| Retrieve contract | `get_contract_version` | Return authorized full content, identifier, immutable version, and extraction limitations. |
| Retrieve standards | `get_review_standard` | Return approved material matching contract type, jurisdiction, and period. |
| Retrieve fallback wording | `get_approved_fallback` | Return only approved alternatives with identifiers and versions. |
| Retrieve history, if needed | `get_agreement_history` | Return authorized prior agreements as historical context, not as an automatic policy override. |

These are interface responsibilities, not predefined product tool names.

Validate tool inputs and outputs. Return explicit errors for denied access, missing records, unsupported formats, and transient failures.

An illustrative retrieval response includes `source_id`, `version`, `location`, `content`, `coverage_status`, and `unavailable_sections`. Define the real schema in the tool implementation. An empty search result, a denied request, and a successfully read document with no applicable clause are different outcomes.

Verify coverage of the full contract, schedules, and attachments. If a knowledge query returns only selected passages, use an authorized full-content retrieval or extraction tool rather than treating the passages as a complete clause inventory.

Apply access restrictions in the backend. Do not expose contract execution, signature, external messaging, or unrestricted update tools.

Complete the architecture's [tool identity and scope record](2.Architecture.md#identity-and-approval-boundaries). [Maker-provided credentials](https://learn.microsoft.com/en-us/microsoft-copilot-studio/configure-no-maker-authentication) can run tools with the connection owner's permissions; signing in to the agent alone doesn't establish requester-scoped access. Assess the impact of requiring live end-user authentication on any background invocation.

If using MCP, review every exposed tool. Use [Build > Tools management](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/tools-manage) to remove unneeded connector actions and turn off individual MCP tools. Keep backend permissions read-only and recheck the exposed surface after changes rather than relying on an instruction to ignore write tools.

If accepting [user-uploaded contract attachments](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/attachments-overview), account for the 16 MiB per-file limit and failure behavior: a failed attachment is skipped while the message continues. Verify all mandatory files/sections against the expected-input manifest. For contracts behind sign-in, use authorized retrieval tools rather than making a private contract URL public to fit URL-attachment processing.

**Exit criteria:** Authorized retrieval succeeds; denied and out-of-scope retrieval remains denied.

## Phase 3 - Configure Instructions and the Review Skill

Configure the agent's role, scope, source requirements, prohibited actions, and clarification behavior.

Add a task skill named `contract-review-against-playbook` through **Build > Skills > Upload a skill**, following [the official upload procedure](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/skills-add-existing). The documented formats are a Markdown skill file or a ZIP containing `SKILL.md` and optional supporting resources. These scenario documents aren't themselves an upload-ready skill package.

For example, begin `SKILL.md` with YAML front matter:

```yaml
---
name: contract-review-against-playbook
description: >-
  Compare an authorized contract with approved, versioned negotiation
  standards and prepare an evidence-linked draft for qualified counsel.
---
```

Follow the metadata with Markdown instructions implementing this procedure, then select **Upload a skill**. **Create from Blank** and **Generate with AI** are also documented authoring options.

1. Confirm required inputs and applicable standards.
2. Retrieve the contract and record extraction limitations.
3. Build a clause inventory and review plan.
4. Retrieve relevant standards and approved alternatives.
5. Compare clauses, classify findings, and withhold replacement wording for counsel-only categories.
6. Check findings against their cited evidence.
7. Produce the review package and unresolved-question list.
8. Hand the draft to qualified counsel.

Require the agent to distinguish verified findings from uncertainty.

Validate each quotation and location against the retrieved contract version, each standard against its applicable library version, and every permitted fallback against the exact approved alternative. Reject unsupported assertions or return them as explicit review questions; semantic plausibility isn't evidence. The [knowledge configuration](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/knowledge-add-existing-copilot) doesn't enforce these output checks for you.

Treat instructions embedded in contracts, attachments, or retrieved material as untrusted document content, not as commands to the agent.

**Exit criteria:** The configured agent produces the agreed output shape without inventing standards or fallback wording.

## Phase 4 - Bound Execution and Recovery

Implement limits for:

- Tool calls.
- Elapsed execution time.
- Retries.
- Document scope.
- Output size.

Enforce limits through supported runtime configuration or an implemented controller/tool layer. Do not assume instruction text alone enforces them.

Retry only recoverable failures. Permission failures, unresolved source conflicts, and missing critical inputs require clarification or escalation.

If durable recovery is implemented, revalidate authorization and source versions after a pause. Otherwise, restart as a new linked run rather than claiming automatic continuation.

Where available and approved, configure [Hooks (preview)](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/hooks-overview) for consistent checks. **Pre tool use** can return `permissionDecision: deny` to block a tool call. **Error** supports `errorHandling` and `retryCount`; **After tool failure** returns `additionalContext`, not those retry-control fields. Follow the [shared event contracts and setup](../../02-patterns/GitHub-Copilot-Harness-Execution/GitHub-Copilot-Harness-Execution-Runbook.md#native-hooks-and-independent-enforcement).

If the Hook fails, times out, or returns an unreadable response, [the agent continues with default behavior](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/hooks-overview#things-to-know). Keep access checks, limits, and mandatory record-update gates independently enforced in the backend/controller. Exercise Hook-failure cases before release; the legal boundary must not disappear when a Hook is unavailable.

**Exit criteria:** Failures produce explicit blocked or partial results without unauthorized workarounds.

## Phase 5 - Implement the Review Gate

Persist the draft through an approved intake or review workflow before relying on it for approval. Agent-created conversation files are limited to 10 MB each and expire 28 days after the conversation's last activity. Split large deliverables and retain the exact submitted versions in approved storage; don't use conversation retention or optional memory as the legal archive.

Separate draft filing and internal reviewer notification into controlled stages:

| Stage | Required control |
|---|---|
| Draft intake | Preserve the exact submitted artifact version and source manifest in approved storage; never mark it approved on arrival. |
| Reviewer notification | Notify only the assigned internal reviewer through an approved destination; never send the agreement to the counterparty. |
| Review and record update | Capture the qualified reviewer's decision and validate authority, artifact integrity, source freshness, and duplicate protection before updating the review record. |

Start intake through an approved review surface or workflow trigger. An agent-generated command or conversational approval is not a substitute for the controlled decision.

Choose and record either a native Workflow or a separate approved review system. For native review, add [Human review > Request for information](https://learn.microsoft.com/en-us/microsoft-copilot-studio/workflows-experience/flows-request-for-information), configure the internal counsel recipient and required decision inputs, then save, publish, and test. RFI sends through Outlook, permits same-tenant recipients only, and uses the first response; it doesn't automatically gather every counsel approval.

For a single-reviewer policy, assign one qualified reviewer and validate the actual respondent's authority through trusted system identity. For multi-reviewer or unanimous approval, implement explicit aggregation or use a review system that supports that requirement. Native [human-input pause/resume](https://learn.microsoft.com/en-us/microsoft-copilot-studio/workflows-experience/flows-request-for-information#run-and-test-request-information-in-your-workflow) isn't general interrupted-run recovery.

If that path can't verify respondent identity, hold the update and obtain the decision through an authenticated review surface; a user-entered Email value isn't proof of reviewer authority.

Create a review surface showing:

- Source clause and location.
- Applicable standard and version.
- Classification and rationale.
- Proposed approved fallback.
- Uncertainty, missing evidence, and conflicts.

Store the generated package as a draft. Approval must be captured by the review system, not inferred from agent output or conversational text.

Before any permitted record update, the workflow verifies reviewer authority, approval validity, artifact integrity, and source freshness.

Use persistent idempotency and backend duplicate protection. After an ambiguous write timeout, reconcile the recorded outcome before retrying.

Implement the [custom artifact, approval, and action-ledger records](../../02-patterns/GitHub-Copilot-Harness-Execution/GitHub-Copilot-Harness-Execution-Runbook.md#custom-approval-and-action-records), including an immutable artifact hash, approved action/payload, expiry, unique action key, and conditional backend updates. A human RFI response doesn't automatically bind an approval to those fields. After a wait, revalidate current source versions and the exact artifact before updating the review record.

**Exit criteria:** Unapproved, changed, expired, or duplicate requests cannot produce an unintended record update.

## Phase 6 - Execute Acceptance Cases

| Case | Expected behavior |
|---|---|
| Contract matches approved standards | Evidence-linked findings with no invented deviations. |
| Material deviation | Flagged using the legal-owned taxonomy and routed for review. |
| No approved fallback | Explicitly states that no approved wording was found. |
| Counsel-only clause with an available alternative | Returns a `RED_LINE` finding and no generated replacement text until handled by counsel. |
| Missing jurisdiction or standards | Requests clarification before analysis. |
| Unreadable attachment | Identifies the unreviewed content without inventing it. |
| Mandatory user attachment is skipped or exceeds 16 MiB | Blocks dependent analysis; no full-review completeness claim. |
| Retrieval returns only selected passages | Does not claim a complete review; retrieves authorized full content or marks the review partial/blocked. |
| Conflicting standards | Surfaces the conflict without silently resolving legal precedence. |
| Prior agreement conflicts with the current standard | Uses the approved precedence rule or escalates; never adopts the prior concession automatically. |
| Unauthorized document | Access remains blocked. |
| Lower-privilege user or missing background credentials | Recorded execution identities remain constrained; no broader-credential fallback. |
| Hook fails, times out, or returns an invalid response | Backend access checks, limits, and write gates still reject invalid work. |
| Plausible but unsupported clause explanation | No invented quotation or legal conclusion; the unsupported claim is omitted or explicitly routed for review. |
| Embedded malicious instruction | Treated as document content; no change to permissions or behavior. |
| Approval followed by artifact change | Commit blocked pending renewed review. |
| Repeated commit request | One business effect with a reconcilable audit record. |
| Write succeeds but the response is lost | Checks the destination/ledger before retrying; no duplicate review-record update. |
| Concurrent resend with the same action key | Backend uniqueness/concurrency protects the record; a different payload under that key is rejected. |
| RFI gets multiple responses | First-response semantics don't count as every reviewer's approval. |
| RFI resumes after a source change or approval expiry | Holds the update pending renewed review. |
| Human response lacks verifiable reviewer identity | Keeps the update blocked until an authenticated, qualified reviewer decision is recorded. |
| Generated package exceeds 10 MB per file | Splits the package and verifies delivery of every required artifact. |

Have qualified counsel independently review a representative sample.

The [Agent Evaluate tab](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/analytics-agent-evaluation-intro) currently scores **General quality**, not direct agreement with expected answers. Record that score separately from counsel-owned clause omissions/misclassifications, source/fallback fidelity, and authorization/approval test outcomes. Run each access test as its intended signed-in user; Evaluate and its tool connections use the current user's profile.

Follow the [shared evaluation lanes and authentication limitations](../../02-patterns/GitHub-Copilot-Harness-Execution/GitHub-Copilot-Harness-Execution-Runbook.md#separate-evaluation-lanes). Don't assume that Workflow Agent node evaluation and the Agent Evaluate tab expose identical methods, or weaken production authentication to make a test run.

Use the [synthetic fixture and expected output](4.Sample-prompts.md#worked-fixture-and-output) as an initial shape test, then replace it with authorized representative documents and legal-owned expected findings.

Measure missed deviations, unsupported findings, evidence validity, correction rate, and review time against the agreed thresholds.

Any unauthorized consequential action or breach of the legal-advice boundary blocks release.

## Phase 7 - Pilot and Operate

Run a limited pilot alongside the existing review process.

Use **Preview** for interactive checks, **Evaluate** for repeatable test sets, and **Monitor** for the published agent. Use the Power Platform admin center for environment capacity and agent monthly limits. A monthly limit with **Stop usage** is separate from the per-run call, time, and retry controls in Phase 4.

The [Monitor success rate](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/analytics-overview#overview-metrics) measures session/run completion, not legal accuracy or counsel approval. Report it separately from legal correctness, evidence coverage, and control acceptance.

Monitor:

- Review preparation time.
- Reviewer corrections and missed deviations.
- Incomplete or blocked reviews.
- Source and tool failures.
- Usage and observable run cost.
- Approval queue age.

Compare matched contract types, sizes, jurisdictional scopes, and reviewer groups against the existing process. Where reviewers share methods or training, compare at team/cohort level to reduce contamination. Record preparation time, total turnaround, review corrections, and credits for all runs, including partial and blocked ones; don't report only successful examples.

When standards change, version them and repeat relevant evaluation cases.

For unsafe behavior, stop new runs and workflow dispatch, restrict write access where necessary, preserve audit records, and restore only a reviewed configuration.

Configuration rollback does not undo completed business actions. Handle those through an authorized correction process.

## Handover

Provide:

- Agent and skill configuration.
- Tool contracts and identity design.
- Approved standards and versioning procedure.
- Acceptance evidence and known limitations.
- Monitoring and escalation procedures.
- Stop, recovery, and change-control procedures.
- Named legal and operational owners.
