# Cowork Enablement Pilot - Overview

## Scenario Overview

**Scenario Type:** Platform enablement, governance and cost-controlled pilot  
**Agent Type:** Microsoft 365 Copilot Cowork (no custom agent build)  
**Primary Tools:** Microsoft 365 admin center, Copilot Cost Management, Microsoft Entra, Azure Cost Management, Cowork  
**Complexity:** Intermediate; the effort is readiness, policy and cost ownership rather than engineering  
**Status:** Documentation available; tenant evidence and sponsor acceptance required

Cowork is available to a licensed user in a few clicks, so the hard questions come first:
who may use it, what it may do, what it costs, who pays, and who is responsible when
something goes wrong. This scenario is the repeatable process for answering them with a
customer. It enables Cowork for a bounded pilot, proves it works under the customer's
own controls, and hands over a decision to expand, extend, pause or stop.

It is the **foundation for the Cowork use-case scenarios**. Run it before, or alongside,
[Chief of Staff](../Chief-of-Staff-Cowork-Agent/1.Overview.md),
[Recurring Analytics](../Recurring-Analytics-Cowork-Agent/1.Overview.md) or
[CRM Account Planning](../CRM-Account-Planning-Cowork-Agent/1.Overview.md), whose runbooks
assume the tenant, governance and billing gates here are already closed.

The journey is **Pilot, Validation, Scale**: estimate before enablement, start with bounded
users and policies, review measured consumption, and expand only when value, support,
security and cost operations are working.

## Who Is Involved

Enablement succeeds or stalls on ownership. Name each role before starting.

| Role | Responsibility |
|---|---|
| Business sponsor | Outcomes, pilot users, success criteria, adoption priority, expansion approval |
| Delivery team (Factory) | Discovery, enablement workflow, validation and handoff |
| M365 / Copilot administrator | Licences, Cowork availability, agent and user-access settings |
| Security / compliance owner | Control posture: web search, plugins, skills, audit, retention, excluded data |
| Billing owner / AI or licence administrator | Billing method, spending policies, limits, alerts, cost review |
| Power Platform administrator | Pay-as-you-go plan and environment reporting, where applicable |
| Azure subscription owner | Subscription, resource group, tags, budgets |
| Change / adoption lead | Training, communications, feedback loop |
| Pilot users | Execute approved scenarios and judge usefulness |
| Support owner | Intake, triage, escalation, known issues, credit-limit requests |

## Expected Outcomes

- Cowork prerequisites validated for the pilot users, with evidence.
- Billing ownership, spending policies, limits, alerts and reporting documented and active.
- Each admin setting configured, or explicitly deferred with an owner and date.
- Pilot users complete approved scenarios; sensitive actions are shown to stop for approval.
- Security, billing, support and adoption owners accept the operational handoff.
- A recorded **expand / extend / pause / stop** decision.

The scenario does not promise a time saving or cost figure. Pilot value and cost are
measured against the customer's own targets and compared with the sponsor's baseline.

## Scope

| In scope | Out of scope |
|---|---|
| Discovery, readiness and licence validation | Building custom skills, plugins or agents (see [Cowork Skill Delivery](../../02-patterns/Cowork-Skill-Delivery-and-Scheduled-Reviews/Cowork-Skill-Delivery-and-Scheduled-Reviews.md)) |
| Tenant, security, governance and network preparation | Remediating tenant-wide permission or labelling debt (identify and sequence it; do not absorb it) |
| Billing method, spending policies, limits, alerts and discovery setting | Pricing quotes or contractual terms |
| Functional and approval-behaviour testing with pilot users | Broad destructive-action testing in production |
| Operational ownership and expansion decision | Production rollout beyond the pilot cohort |

Licensing, billing meters, portal UI and availability change often. Treat every
product statement here as a prompt to verify against current Microsoft documentation in
the customer's tenant, not as a guarantee.

## What Must Be True Before Anyone Is Enabled

1. **A named sponsor, pilot group and 2-3 documented use cases.** If any is unknown, stop.
2. **A billing owner and a funding path.** Cowork needs a Microsoft 365 Copilot licence
   **and** usage-based billing in Copilot Credits. A licensed user with no policy or funding
   is a support case, not a pilot.
3. **An accepted security posture** for web search, plugins, custom skills, Teams posting,
   external email, file changes and excluded data classes. If security cannot approve it,
   do not enable users.
4. **Reviewed permissions** on in-scope SharePoint, OneDrive and Teams content. Cowork acts
   with the user's access, so oversharing becomes visible, not new.
5. **A support path** users can find, including how to request more credits.

## Key Design Points

- **Discovery is a control.** Decide whether Cowork stays hidden until billing is ready,
  is communicated to the pilot only, or is broadly visible. Visibility ahead of budget
  ownership creates unplanned demand.
- **Spending policies are the cost guardrail.** Scope by security group, set a policy limit
  and a per-user limit, and choose the services each policy covers. Avoid accidental overlap
  and review *Auto-apply new services* deliberately.
- **`/cost` is a user signal, not billing.** Official reporting, chargeback and
  reconciliation come from Cost Management and the billing portals.
- **Intensity drives cost.** Document generation, deep research, scheduled prompts and
  event-driven tasks consume materially more than simple tasks; estimate and review them
  separately.
- **Approval cards are a safety control to verify, not assume.** Prove, per action type,
  that sensitive actions stop for explicit approval, and train users on "do not ask again".
- **Scale is gated.** Expansion depends on exit criteria, operating reports, sponsor
  approval and a working limit-increase process, not on enthusiasm.

## Common Failure Patterns

| Pattern | Consequence | Prevention |
|---|---|---|
| Cowork visible before policies exist | Unmanaged consumption and surprise demand | Keep discovery restricted until policies and alerts are live |
| One shared budget, no per-user limit | One user exhausts the pilot | Set per-user limits; review weekly |
| Overlapping policy membership | A user lands on an unintended policy | Design membership; learn the precedence rules |
| Wide default spending policy left unchanged | Unintended scope and cost | Constrain or explicitly accept the default |
| Treating `/cost` as billing | Wrong chargeback figures | Train the distinction; reconcile in Cost Management |
| Scaling before governance | Support, cost and security issues after rollout | Gate expansion on the decision record |
